Import `DurabilityLog` from `durability`. Use retained records when consumers need independent positions and replay. See the [event-stream composition](/compositions/event-stream/).

## How it uses your Durable Object

`DurabilityLog` adds no stream service of its own. It uses the Durable Object it is constructed in:

- **`ctx.storage.sql`** holds the hot records, the offset sequence, every consumer's cursor, the index of flushed segments, the range of a cold flush still in progress, and, with leases, each held range, all keyed by the log's [channel](#channels). A partition's history and positions belong to that object alone.
- **The object's one alarm** is never set by the log. The log joins the object's one scheduler and claims its channel there, but registers no due work with it, so retention runs only when your code calls `trim()`, typically from a `DurabilityAlarms` handler whose `alarm()` your class delegates to `scheduler.alarm()`.
- **RPC from outside:** producers call your object to append and pollers call it to read and commit. Cold segments are the only external I/O, written by `trim()` and read back for consumers behind the hot window.
- **The live instance** holds only configuration. Lease expiry is a stored timestamp rather than a timer, so eviction loses nothing the log needs. A producer whose reply was lost retries with the same deduplication keys.

## Behind the scenes

**Durable state:** `durability_log_records` holds hot records by `(channel, offset)`, with a retained deduplication key unique within the channel. Cursor, sequence/byte-count, and cold-segment metadata tables track readers and storage, and `durability_log_pending_flushes` holds the range of a cold flush that has not finished, each keyed by channel first. Optional leasing adds durable lease/allocation tables, keyed the same way.

`append()` allocates offsets and inserts the batch atomically. Reading does not acknowledge anything: `commit()` only advances one consumer cursor. Optional `lease()` persists an exclusive range before returning records; fresh batch IDs fence expired or superseded holders, and acknowledgements advance only across contiguous settled ranges.

**Not an automatic background loop:** the log joins the object's one scheduler but does not register a due-work participant. Nothing periodically calls `trim()` for you. Compose a named alarm when retention needs a clock.

**Cold-storage failure:** the run's first and last offsets are recorded before the external segment is written, and its locator is committed, its hot records removed, and the recorded run cleared in one transaction. A failed write preserves hot data. A crash after the remote write may repeat it, and the retry carries exactly the same records under the same first offset, so a key that refuses to overwrite is safe. The cold store's lifecycle and removal of obsolete locators are application policy.

**Lifetime:** retention ignores consumer cursors. A slow reader can lose readable history and gets `LogTruncatedError`. Append deduplication ends when the original hot record is flushed or deleted. Processing can repeat after an effect succeeds but before cursor/lease settlement, so effects still need idempotency.

Implementation: [`log/index.ts`](https://github.com/avenceslau/durability/blob/main/packages/durability/src/log/index.ts) (`appendRecords`, `read`, `trim`, `lease`, `ack`, `nack`).

## Retained log

Fanout deletes a record once every target settles it, which is what a work queue wants. A log wants the opposite: records are **retained** so a consumer can rewind, a new consumer can start from the beginning, and several consumers can read the same history at different speeds. `DurabilityLog` is that second shape, and it attaches to the same scheduler.

```ts
import { DurabilityLog, DurabilityScheduler, type LogRecord } from 'durability';

export class Partition extends DurableObject<Env> {
  private readonly scheduler = new DurabilityScheduler({ context: this.ctx });
  private readonly log = new DurabilityLog<Event>({
    scheduler: this.scheduler,
    retention: {
      maxAgeMs: 7 * 24 * 60 * 60 * 1_000,
      maxRecords: 100_000,
      maxBytes: 512 * 1024 * 1024,
    },
    // Flushed records stay readable: `write` returns a locator the log keeps,
    // and `read` hands the segment back when a consumer asks for it.
    cold: {
      write: async ({ channel = 'default', records, firstOffset }) => {
        const locator = `segment/${this.ctx.id}/${encodeURIComponent(channel)}/${firstOffset}`;
        await this.env.COLD.put(locator, JSON.stringify(records), {
          onlyIf: { etagDoesNotMatch: '*' },
        });
        return locator;
      },
      read: async (locator) => {
        const stored = await this.env.COLD.get(locator);
        return stored ? await stored.json<LogRecord<Event>[]>() : undefined;
      },
    },
  });

  append(events: Event[]) {
    return this.log.append(events.map((body) => ({ body })));
  }
}
```

`append` mirrors `enqueue`: the batch commits atomically, definite input rejections return `success: false`, and storage or commit uncertainty throws. It returns each record's **offset** in input order. Passing a `deduplicationKey` makes an append idempotent — re-appending an existing key returns its original offset and consumes no new one — so a producer that retries after an uncertain commit does not duplicate records.

Consumers **pull** and own their position:

```ts
const from = (await log.cursor('search')) ?? (await log.bounds()).oldestOffset;
const page = await log.read({ from, limit: 100 });
await index(page.records);
await log.commit('search', page.nextOffset);
```

`commit` only ever advances, so a late or duplicated commit cannot rewind a cursor. Cursors are independent: `log.cursors()` returns every consumer's position, and `log.load()` reports the furthest-behind cursor as backlog so routing can weigh partitions by consumer lag rather than by queue depth.

### Retention is not acknowledgement

Records leave only through `trim()`, which enforces `maxAgeMs` and `maxRecords`, oldest first. Retention is deliberately not automatic, because no capability should schedule work an application did not ask for. A `DurabilityAlarms` handler is the composition that gives it a schedule, and it keeps `alarm()` a pure delegation:

```ts
private readonly alarms = new DurabilityAlarms({
  scheduler: this.scheduler,
  handlers: { compact: () => this.log.trim() },
});

alarm(info?: AlarmInvocationInfo) {
  return this.scheduler.alarm(info);
}
```

`maxBytes` is the budget that actually matters, because a Durable Object holds a hot window rather than an unbounded log. It counts payload bytes held in the object and is capped at `maxLogBytes` (1 GiB), leaving room for the other capabilities sharing that object's storage.

### Flushing to cold storage, and reading it back

Retention has two possible destinations. Without `cold`, expiring records are **deleted**. With `cold`, they are **flushed** and stay readable:

```ts
type LogColdStorage<Body> = {
  write(segment: LogSegment<Body>): Promise<string>;
  read(locator: string): Promise<LogRecord<Body>[] | undefined>;
};
```

`write` receives one contiguous run of records, oldest first, with the log's `channel`, and returns a locator — any string identifying where the segment went. The log records the run's first and last offsets durably **before** calling `write`, then stores the locator in a durable segment index, deletes the records, and clears the recorded run in one transaction, so a crash at any point leaves either the records in the object or a written, readable segment, never records pointing nowhere. A failed write propagates with the records still in the object, so configured storage cannot be skipped. Writes are at-least-once, but a retried write for a given first offset always carries the same records — whether the earlier write failed, lost its response, or the object restarted, and however many records were appended since — so key segments by first offset and refuse to overwrite. R2's conditional `put` returns `null` when it refuses; the example above ignores that result, which is safe because the object already stored holds the same records.

`read` is what makes a flush **rehydratable**. A consumer reading a flushed offset gets its records back transparently, so falling behind the hot window is no longer fatal; `bounds()` reports `oldestOffset` (oldest readable, including flushed segments) alongside `hotOffset` (lowest offset still in the object). Cold reads cost a round trip and open input gates, so they serve only consumers that fell behind — never the hot path.

External storage expires on its own schedule, so mirror a lifecycle rule with `forgetColdBefore(offset)` to drop stale index entries. Nothing calls it automatically. Returning `undefined` from `read` is also honoured: a segment the index outlived surfaces as truncation rather than a silent gap.

Retention still **ignores cursors**, exactly as a log should: a consumer slower than everything readable loses records. It learns loudly rather than silently skipping, because reading below the oldest readable offset throws `LogTruncatedError` carrying `requestedOffset` and `oldestOffset`. Leased consumers learn the same way: when a range awaiting redelivery (nacked or expired) was trimmed, `lease()` throws `LogTruncatedError` once, drops the trimmed offsets from the range, and the next call carries on from what is still retained. A leased consumer's cursor moves past offsets trimmed before anyone leased them. Compare `bounds()` against a cursor to detect the risk before it happens.

### Leases for parallel consumers

`read` plus `commit` is enough for one worker per consumer. It is **not** enough when two pollers share a consumer name: both read the same page and both process it. Leases close that gap.

```ts
const lease = await log.lease('search', 100);
if (lease) {
  try {
    await index(lease.records);
    await log.ack('search', lease.batchId);
  } catch {
    await log.nack('search', lease.batchId);
  }
}
```

`lease` claims a range of offsets durably **before** returning the records, so a second caller gets the next range or `undefined` rather than the same offsets. That holds for overlapping calls too, including ones that read a flushed range from cold storage: the transaction that records the range first checks that no other call took those offsets or the last free slot meanwhile, and selects again if one did. `undefined` means nothing is available right now — either the consumer is at `maxParallelism` or the log has no unleased records — so treat it as a signal to back off.

A range is held until it is acked, nacked, or its lease expires after `leaseMs`. Redelivery always issues a **fresh `batchId`**, which fences the previous holder: its `ack` throws `LogLeaseError` rather than committing a range someone else now owns. Double settlement throws for the same reason, and so does an `ack` or `nack` naming a consumer other than the one holding the batch, which leaves the range untouched.

`maxParallelism` lets one consumer hold several ranges at once, and `ack` commits only over an **unbroken run** of settled ranges starting at the cursor. Acking a later range while an earlier one is still in flight advances nothing, so parallelism never skips offsets. Leases are durable, so eviction mid-flight does not release a range early, and a range that retention flushed while it was held is rehydrated on redelivery.

A range that keeps failing would be redelivered forever. `maxAttempts` bounds that, but only together with `onPoison`: without somewhere to send the records, blocking the consumer beats silently dropping them. With both set, an exhausted range is marked skipped — durably, before the callback runs, so a failing handler cannot resurrect it — and the commit then runs over it like an acked one.

Leases are opt-in. Without the `leases` option no lease tables are created, `read`/`commit` behave exactly as before, and the lease methods throw.

### Channels

The `channel` option names a log within its object and defaults to `default`; it must be a non-empty string. Several logs can share one Durable Object and its scheduler, one instance per channel. Constructing a second `DurabilityLog` on a channel already attached to the object throws `DurabilityLog for channel "audit" is already attached to this scheduler`.

```ts
private readonly audit = new DurabilityLog<AuditEntry>({
  scheduler: this.scheduler,
  channel: 'audit',
  retention: { maxRecords: 10_000 },
  cold,
});
```

Each channel has its own offset counter, starting at 0, and its own deduplication keys, consumer cursors, segment index, leases, and allocations. The same consumer name, deduplication key, or batch ID in two channels refers to unrelated state. `trim()` applies the instance's retention to its own channel only, and `maxBytes` counts only that channel's payload bytes, so an object holds up to the sum of its channels' budgets. `bounds()`, `cursors()`, and `load()` report only the instance's channel.

Two channels both flush segments that start at offset 0, so cold storage shared between them must put the segment's `channel` in the key it writes, as the example above does. Otherwise one channel's write overwrites the other's segment or, with a conditional put, is refused. A stored locator is read back only by the channel that wrote it.

Upgrading moves existing records, cursors, segments, leases, and allocations to `default` unchanged. A channel that no instance attaches keeps its rows, and since the log schedules no work, nothing waits on it. A schema downgrade refuses to run while a non-default channel has records, cursors, segments, an offset counter, leases, or allocations.

### What it is not

There is no per-record retry, timeout, or dead letter here: a log tracks positions, not attempts. When a single record must be retried independently of its neighbours, that is fanout's job, and the two compose on one object.

There is also no key compaction. `deduplicationKey` is unique per retained record, which is the opposite of a compaction key, and deduplication lasts only while the original record is retained — re-appending a key after its record was flushed or deleted creates a new record.
