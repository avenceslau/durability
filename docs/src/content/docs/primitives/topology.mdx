Import `DurabilityTopology` from `durability/experimental` and pin an exact version. Use one coordinator to own a group's membership and publish it for readers, optionally pushing shared state to members.

## How it uses your Durable Object

`DurabilityTopology` turns one Durable Object into the coordinator of its groups. It uses that object, and only reads or calls the others:

- **`ctx.storage.sql`** holds the membership, state values, and write records in `durability_topology_*` tables, plus every staged publication and delivery as rows in the shared `durability_outbox` table. They commit in one transaction with each change.
- **The object's one alarm** is set in that same transaction to the earliest pending outbox row, so publication and deliveries resume after eviction. Your class's `alarm()` must delegate to the object's scheduler, which the helper joins.
- **The live instance** holds the in-flight store writes, member calls, and their timeouts. An eviction loses them; the outbox rows and write records in storage are what recovery relies on.
- **Other objects and Workers** never share that storage. Members receive state values over RPC and must check versions themselves; readers use `DurabilityTopology.client`, which reads the published copy and never calls the coordinator.

## Behind the scenes

**Durable state:** `durability_topology_groups` and `durability_topology_states` hold membership and state channel values. `durability_topology_writes` tracks publication requests that could still land after timeout or eviction. Every row carries an `owner_channel`, the [instance channel](#instance-channels) it belongs to, as part of its key. Internal [outbox](/primitives/outbox/) channels drive group publication and per-member state delivery.

`update(group, next)` evaluates your synchronous draft inside a transaction. It commits membership changes, changed state values, and staged publication/deliveries together. Membership versions advance on actual membership changes; outbox delivery versions prevent applying stale channel values at members.

**Recovery:** a failed member retries independently through its outbox entry; newer values coalesce. An active member participates in writes and reads; draining members remain in the read set. Already in-flight deliveries may still arrive after removal.

For unconditional publication stores, write tracking uses a bounded landing deadline before repairing uncertain old writes. An older write arriving beyond that window can still overwrite a newer snapshot; only a version-aware sink removes that bound. The client rejects same-coordinator version regressions in its own cache but cannot make a stale store globally consistent.

**Reader state is in memory:** TTL caches and fallback decisions are not durable membership. The client reads the published store rather than the coordinator, unless application fallback deliberately adds that dependency.

Implementation: [`topology/index.ts`](https://github.com/avenceslau/durability/blob/main/packages/durability/src/topology/index.ts), [`topology/client.ts`](https://github.com/avenceslau/durability/blob/main/packages/durability/src/topology/client.ts).

## Shard topology (experimental)

`DurabilityTopology` is for work spread over several Durable Objects (shards) whose membership changes over time, where something else needs to reach them: a router picking a shard for a write, a reader querying every shard, or a coordinator pushing configuration to all of them. It lives in `durability/experimental`, so pin an exact version.

One coordinator Durable Object holds each group. It is the only thing that can change or publish that group. Readers never call it: they read the snapshot it published.

```ts
import {
  DurabilityTopology,
  type TopologyStateUpdate,
} from 'durability/experimental';

export class Coordinator extends DurableObject<Env> {
  private readonly scheduler = new DurabilityScheduler({ context: this.ctx });
  private readonly topology = new DurabilityTopology({
    scheduler: this.scheduler,
    publish: {
      write: (snapshot, encoded) =>
        this.env.TOPOLOGY.put(`topology/${snapshot.group}`, encoded),
      delete: (group) => this.env.TOPOLOGY.delete(`topology/${group}`),
    },
    states: {
      limits: {
        deliver: (member, update: TopologyStateUpdate<Limits>) =>
          this.env.SHARDS.getByName(member.id).applyLimits(update),
      },
    },
  });

  createTenant(tenant: string, limits: Limits) {
    return this.topology.update(tenant, () => ({
      members: [0, 1, 2].map((n) => ({
        id: `${tenant}-${n}`,
        state: 'active' as const,
      })),
      states: { limits },
    }));
  }

  retireShard(tenant: string, shard: string) {
    return this.topology.update(tenant, ({ members }) => ({
      members: [
        ...members.map((m) =>
          m.id === shard ? { ...m, state: 'draining' as const } : m
        ),
        { id: `${tenant}-${members.length}`, state: 'active' },
      ],
    }));
  }

  deleteTenant(tenant: string) {
    return this.topology.delete(tenant);
  }

  alarm(info?: AlarmInvocationInfo) {
    return this.scheduler.alarm(info);
  }
}
```

The coordinator has three methods:

- `update(group, next)` runs `next(current)` inside one storage transaction and commits its draft, staging publication and deliveries in the same transaction. `current` holds the members and the current state values. The draft can set `members`, `states`, or both, and `next` must return synchronously, so nothing interleaves between reading and writing. Membership changes bump the group's `version`; unchanged drafts do not. After the commit, one publish is attempted: `published: false` means the snapshot is not yet final in the store, because the write failed or an older write may still land over it. The change is committed either way, and the outbox keeps going until it is. An empty member list is rejected; use `delete`.
- `delete(group)` drops the members and state values, cancels pending syncs, and asks the publisher to delete the snapshot. Versions keep counting, so a recreated group is newer than anything a reader cached.
- `snapshot(group)` reads the group inside the coordinator. It is not a lookup path for other Workers.

An `active` member is in the write set and the read set. A `draining` member is only in the read set: it receives no new work but still holds data, so queries must still reach it. Members leave the read set only when a draft omits them.

### When to use it

Topology is for when something needs the list of shards. A shard that only does work when a caller reaches it, and only talks to a coordinator whose name it can derive, does not need one: create it on demand.

| Need                                                                                                                               | Use                                                                                      |
| ---------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| A shard does work when a caller sends it something                                                                                 | Nothing: address it by name, for example with `DurabilityRouting`                        |
| A shard asks a central object for something it needs, such as permits or capacity                                                  | `DurabilitySemaphore`: shards pull, and the holder learns about them from their requests |
| A caller must pick among a group's current shards                                                                                  | Topology membership                                                                      |
| A reader must reach every shard that may hold data                                                                                 | Topology membership, including `draining` members                                        |
| Every shard must hold the same data before any caller reaches it, such as schedules it runs by itself or configuration it enforces | A topology state channel                                                                 |

A state channel sends one value to every member in its role. Values that differ per shard, or that must be accounted for in both directions (granted, used, returned), do not fit it; that is the semaphore's model.

A shard created on demand can still join its group, so readers can find it later: its first request can call the coordinator, which adds it with one `update`. Only do this when a reader needs it.

### Publishing

`publish.write` receives the snapshot and an `encoded` string. Store `encoded` as is; it is the only format the client reads, and no encoder is exported, so only the coordinator can produce one. It carries the coordinator's Durable Object ID, because versions only compare within one coordinator: if a group moves to another coordinator, its versions start over, and readers accept the new snapshot. Publication runs on a `DurabilityOutbox` channel (`durability.topology` for the default [instance channel](#instance-channels)) keyed by group, so it shares the outbox's guarantees: only the newest snapshot of a group is pending, publish calls for the channel run one at a time, and attempts never stop (`retries.delay` controls backoff). The outbox expects sinks to keep the highest version, which a plain `KV.put` cannot, so the topology closes that gap itself, durably:

- Every write is recorded in storage before it starts and forgotten once it settles.
- A record that outlives its write, because the write timed out or the object was evicted mid-write, means an older snapshot may still land. A newer write is then not acknowledged until that record's landing deadline has passed, and is written again at that point.
- An abandoned write that settles while the object is still running restages the latest snapshot immediately.

The landing deadline is the write's start plus `attemptTimeoutMs` plus five minutes. A write that lands later than that can still overwrite a newer snapshot until the next change; only a sink that keeps the highest version avoids that bound. `attemptTimeoutMs` bounds one write.

### State channels

Each entry in `states` is a channel whose latest value every member converges to. `members: 'write'` (the default) reaches active members; `'read'` reaches draining members too. Setting a value delivers it to every member in the role. A member that enters the role receives the current value in the same transaction that added it, so a new shard never starts with an old value. A member that leaves the role has its pending delivery discarded; one already in flight may still arrive. Each state channel is its own outbox channel (`durability.topology.<name>` for the default instance channel) keyed by group and member, so every member is retried independently; `attemptTimeoutMs` bounds one delivery, and a member that hangs holds up the rest of its batch only until then. Setting a channel to the value it already has delivers nothing.

Only the latest value is delivered, and a timed-out delivery may still arrive after a newer one. `version` is the outbox version, which only increases. Apply an update only when it is newer than the last one applied, in the same transaction:

```ts
applyLimits(update: TopologyStateUpdate<Limits>) {
  this.ctx.storage.transactionSync(() => {
    const applied = this.ctx.storage.kv.get<number>('limits:version') ?? 0;
    if (update.version <= applied) {
      return;
    }
    this.ctx.storage.kv.put('limits', update.value);
    this.ctx.storage.kv.put('limits:version', update.version);
  });
}
```

`onLifecycleEvent` receives the outbox events of those channels: `channel` is the outbox channel name of the publication or state channel, and `id` is the group, or `[group, member]` as JSON for a delivery.

### Instance channels

State channels are the values pushed to members. Instance channels are a different thing: the `channel` option, `default` unless given one, lets several topologies share one coordinator and scheduler, for example an application's and a library's. Each instance channel holds one topology, with its own groups, state values, versions, stale-write fencing through its write records, publisher, and deliveries. The same group and state names in two instance channels are unrelated, and deleting or updating one leaves the other alone. Constructing a second topology on an instance channel already in use throws `DurabilityTopology for channel "<channel>" is already attached to this scheduler`, with or without a publisher.

```ts
private readonly libraryTopology = new DurabilityTopology({
  scheduler: this.scheduler,
  channel: 'library',
  publish: {
    write: (snapshot, encoded) =>
      this.env.TOPOLOGY.put(`library/${snapshot.group}`, encoded),
    delete: (group) => this.env.TOPOLOGY.delete(`library/${group}`),
  },
});
```

Snapshots do not name the instance channel, and both instances record the same coordinator ID, so instances that share a read store must publish under different keys, as above. The default instance keeps the outbox channels `durability.topology` and `durability.topology.<state>`. Any other instance uses the JSON outbox channel names `["durability.topology", <channel>, "publication"]` and `["durability.topology", <channel>, "state", <state>]`, so two instances or states never share an outbox channel. Pending publications and deliveries of an instance that is no longer constructed are kept and postponed by the outbox, never handed to another instance.

The channel migration adds `owner_channel` to the three topology tables and moves existing groups, states, and write records to `default`. A schema downgrade refuses to run while rows of another instance channel exist, including the rows `delete` leaves behind; delete those rows explicitly before rolling back.

### Reading

Stateless Workers read through a client. It has one method:

```ts
const topology = DurabilityTopology.client({
  read: (tenant) => env.TOPOLOGY.get(`topology/${tenant}`),
});

const { members } = await topology.get(tenant);
const writable = members.filter((member) => member.state === 'active');
const shard = writable[Math.floor(Math.random() * writable.length)];
```

Routing, querying every member, and resolving stubs are ordinary code over `members`.

The client caches each group in the isolate for `ttlMs` (default 30 seconds, jittered by ±20%), shares one read between concurrent callers, and never replaces a snapshot with an older version from the same coordinator. A missing or failed read is remembered for `negativeTtlMs` (default 5 seconds). Reads time out after `readTimeoutMs` (default 1 second).

When the published copy is missing, invalid, slow, or the read throws, `get` throws `TopologyUnavailableError` with a `reason`. Every fallback is opt-in, and they run in this order:

1. `staleIfErrorMs` serves this isolate's last good snapshot for that long after it expired. It never applies to a missing group.
2. `seed(group)` derives members locally, without I/O.
3. `fallback(group, reason)` is application code and is not cached.

The client never contacts the coordinator. Wiring `fallback` to it moves every reader onto one Durable Object at the moment the read store is struggling, so prefer failing or serving stale. `onFallback` reports each fallback and its source.
